# TASK-005: контракт реализации и сохранность

План до кода сохранён в карточке. Источник требований — PRODUCT и TASK-005, не этот документ.

- В DTO `crit` — canonical decimal string **целых тысячных**, либо `null` (unknown/noncritical). Формы принимают десятичную точку/запятую и округляют вверх до0,001. Например0,0441→`"45"`, отображение0,045. Новым 🧿/💢 нужен явный крит, включая`"0"`; прежняя exact receipt проверяется до этого нового требования. Неизвестное никогда не становится нулём автоматически.
- `POST /api/fuse-preview`: `{revision,experiment,fuse:{kind,targetTier,count,items:[{id,quantity,worn}]}}`. Та же сессия/Origin/CSRF/account защита, но без записи revision, receipt или истории. `POST /api/commands` action`{type:"fuse",fuse:...}` повторяет расчёт внутри IMMEDIATE. Клиентские цена/результат не принимаются. `items` — упорядоченный разрешённый пул. Batch `worn` — максимум разрешённых надетых; фактически`max(0,used-(stock-equipped))`. В одиночном `craft` поле`worn` по-прежнему задаёт точное количество.
- Plan возвращает selected(allowed/allowWorn/used/worn/unused/remaining), ordered steps(inputs/outputs/count/unitPrice/price), final outputs и полную цену. Готовые selected units нужной ступени предшествуют новым intermediate; объединять несоседние промежуточные runs до формирования следующей тройки нельзя.
- Ввод обычных целых —128цифр; нормализованный crit —131цифра тысячных. Производные значения не ограничены128. Пул/refinement quantity допускает256цифр, чтобы расходовать уже агрегированный запас; максимум1000выбранных групп и10000сегментов плана ограничивают размер запроса/работы, а не количество игровых экземпляров. HTTP body1MiB. Все ограничения проверяются до BigInt/тяжёлой работы и транзакционных изменений.
- `original.put` новой записи или положительная дельта quantity при тех же kind/tier/value/crit добавляется одновременно в original/work. Уменьшение/delete/смена атрибутов started меняют толькоoriginal. `original.crit` — отдельное бесплатное уточнение`{id,quantity,crit}`: оно не трактуется как новая партия и в started не меняетwork. `work.crit` —`{id,quantity,worn,crit}`, гдеworn точный; допускает толькоunknown→known, split/merge без сброса, сохраняет gear/history/spent.
- SQL work_lots хранит непересекающиеся компактные origin/start/quantity диапазоны с атрибутами; worn_ranges ссылается на физические диапазоны. Origin выдаётся на добавленную партию/итоговыйrun, не на экземпляр. FIFO внутри одинаковых атрибутов — технический порядокborn/start, без оптимизации статов. History сохраняет consumed ranges с исходными атрибутами, final output origins и pre-wear. Undo удаляет именно эти origins после любых уточнений/слияний, возвращает входы из snapshots и прежнюю экипировку. Позднейшие пополнения имеют другие origins и сохраняются. Изменение текущего уровня не отменяется.
- Миграция2/3→4: reverse quantities определяет baseline, forward replay строит виртуальное происхождение старых single outputs. Проверяются формулы/цены/количества/экипировка; никакой крит из истории не угадывается. Все промежуточные schema migrations и final user_version — одна outer IMMEDIATE; revision увеличивается один раз. Ошибка возвращает прежнюю логическую схему, таблицы и receipt bytes. Включение WAL может изменить SQLite header ещё до миграции; неизменность контейнерного бинарного файла не заявляется. Встроенные fault hooks доступны лишь через constructor import в тестах, не через production env/API.

Существующие regression assertions обновляются только для согласованных изменений: новые DTO fieldscrit/stats, schema4 вместо3, новые критические input rows с явным0, displayKind вместо старых glyphs и положительное пополнение6→9 в started. Старые golden receipts/SQL fixtures и frozen Sites не переписываются.
