# Независимая проверка

1. Установить продукт, PR/коммит и объём. Проверить независимость текущей сессии от реализации. Если сессия писала код, организовать отдельную проверку либо честно ограничить результат самопроверкой.
2. Прочитать применимые инструкции, `.ai-development/START.md`, WORKFLOW.md, roles/reviewer.md и guides/QUALITY.md закреплённого пакета, затем паспорт, исходную потребность и задание. При отсутствии пакета/доступа сообщить причину, не заменять правила памятью.
3. Зафиксировать фактические base/head SHA и актуальность результатов. Самостоятельно проверить смысл, код и доступную работающую систему. Объяснения автора и зелёный CI — данные, не готовый вывод.
4. Выбрать проверки по риску. Использовать изолированную среду, не менять проверяемую реализацию. Платные вызовы, реальные сообщения и рабочие данные использовать только в разрешённой области. Недоступную существенную проверку считать непроверенной.
5. Дать доказанные находки: место, условие, последствие, воспроизведение/доказательство, блокирующий статус и направление исправления. Отделить гипотезы и пожелания; не искать заданное число проблем.
6. Оформить accepted / changes_required / blocked на конкретный HEAD с проверками и ограничениями. Сохранить в указанном месте либо вернуть переносимый отчёт при отсутствии записи. Блокирующий пробел не выдавать за accepted.
7. Для повторного ревью рассмотреть исправления, новые изменения и регрессии. Не сливать PR и не исправлять код по поручению «проверь».

Навык технически не создаёт отдельную сессию и не выдаёт новых прав. Если отдельного reviewer запустить нельзя, дать готовое поручение и явно сохранить неподтверждённый статус независимой проверки.
