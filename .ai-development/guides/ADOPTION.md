# Подключение и обновление

Эта процедура предназначена для управляющего/агента с доступом к репозиторию. Владелец использует готовые сообщения из README. Подключение стандарта само по себе не разрешает функциональные изменения, слияние или выпуск продукта.

## Новый продукт

1. Прочитать START.md общего репозитория через доступную авторизованную интеграцию, определить полный коммит источника и VERSION. До создания репозитория можно собирать требования в роли product; затем сохранить их без потери принятых решений.
2. Получить рабочую копию источника на выбранном коммите и целевой репозиторий. Не печатать токены. Убедиться, что source чистый, а target — отдельный корень Git. Не исполнять непроверенный удалённый shell через curl pipe.
3. Запустить план подключения:

```bash
python3 /path/to/ai-development/scripts/adopt.py --target /path/to/product
```

4. Проверить план, затем повторить с `--apply`. Это записывает только локальные файлы, не коммитит, не пушит, не создаёт репозиторий и не меняет рабочий сервер.
5. Заполнить `.delivery/PROJECT.md`: авторитетные документы, роли/разрешения, технические ограничения, среда владельца, фактически доступные возможности. Перенести согласованные требования в PRODUCT.md. Команды тестов/выпуска заполнить после выбора технической основы, до зависимой реализации/доставки; неизвестное не выдавать за настроенное.
6. Проверить конфликт инструкций и доступность нужных файлов из новых сессий. Подготовить среду по [ENVIRONMENTS](ENVIRONMENTS.md) до зависимой реализации. Сохранить изменения в целевой репозиторий по полномочиям и передать владельцу готовые стартовые сообщения. Если поручена готовность в main и слияние разрешено, закончить его самостоятельно после проверки.

Источник должен быть закоммичен и чист. Скрипт сохраняет VERSION, полный source_commit и хеши управляемых файлов в `.ai-development/manifest.json`. В продукт копируются правила/роли/руководства/шаблоны, инструменты и навыки. AGENTS.md и CLAUDE.md получают выделенные блоки; существующий текст сохраняется. В `.delivery` создаются только отсутствующие начальные документы; задача и отчёт создаются по необходимости.

После подключения точка входа — `.ai-development/START.md`. Копия стандарта не редактируется для настройки продукта: отличия фиксируются в паспорте/применимых инструкциях с основанием. Прямое изменение управляемых файлов будет обнаружено при обновлении.

## Существующий продукт

Сначала прочитать его инструкции, требования, очередь, открытые PR, ограничения и подтверждённый выпуск. Подключать отдельным изменением, не добавляя новую функциональность.

Скрипт сохраняет имеющиеся файлы `.delivery` и текст AGENTS/CLAUDE, но не умеет автоматически разрешать смысловые противоречия. Управляющий обязан сопоставить их с WORKFLOW.md, сохранить действующие разрешения и требования, явно согласовать существенный конфликт. Если уже есть SPEC/BACKLOG/STATE/runbook, указать их в паспорте и убрать неиспользуемые новые шаблонные дубликаты до коммита. Не переписывать принятую историю.

Проверить зависимости незавершённых задач; не менять их правила приёмки скрытно. Результат подключения — известная версия стандарта, корректный паспорт и понятные точки входа, а не формально созданная папка.

## Если нет локального checkout или Python

Через GitHub-интеграцию получить файлы **одного полного SHA** источника. Воспроизвести план scripts/adopt.py: копия поддерживаемого пакета в `.ai-development`, три навыка в `.agents/skills` и `.claude/skills`, выделенные блоки в корневых инструкциях, отсутствующие документы `.delivery`. Сохранить manifest с SHA-256 фактических байтов. Не имитировать manifest и успешный запуск скрипта; при невозможности вычисления/проверки использовать среду с checkout либо передать конкретное поручение Codex. Изменения существующих файлов выполнять с проверкой актуального blob/HEAD и сохранением чужих изменений.

## Обновление стандарта

1. Прочитать CHANGELOG нового коммита общего стандарта и оценить совместимость с продуктом. Выбор версии — явное решение management в пределах полномочий; существенное изменение политики согласуется с владельцем.
2. Получить чистый checkout нового источника. Из него выполнить:

```bash
python3 /path/to/new-standard/scripts/adopt.py --target /path/to/product --update
```

3. Скрипт проверяет хеши старых управляемых файлов, отсутствие чужих файлов и целостность своих блоков. При конфликте останавливается до записи. Не удалять локальную правку, чтобы обойти проверку: выяснить её смысл, перенести нужное в настройки продукта либо подготовить осознанное ручное обновление с сохранением истории.
4. После проверки выполнить с `--update --apply`, проверить diff и структуру пакета, актуализировать настройки/поручения и сохранить отдельным изменением. Повторное обновление той же версией/коммитом не создаёт изменений. Скрипт не выполняет сеть, merge или release.
5. Проверить новые сессии и навыки там, где поменялся механизм загрузки. Установленные личные навыки обновляются отдельно поддерживаемым механизмом; копия в GitHub не является доказательством установки.

## Версионирование и развитие

MAJOR — несовместимое изменение обязанностей/полномочий/форматов, MINOR — совместимое расширение, PATCH — исправление. VERSION вместе с полным SHA определяет подключённый пакет; тег удобен, но не обязателен и не заменяет SHA. Не создавать public Release или менять видимость без поручения.

Рабочие изменения стандарта проходят структурные проверки, проверки инструмента подключения и содержательное чтение затронутых ролей/README. Для навыков — проверку триггеров и выполнения на независимых безопасных примерах. Это контроль качества готового стандарта, не обязательный пилот продукта.

Не добавлять новый документ/статус/агента без понятной пользы. Общие правила редактируются в источнике и распространяются контролируемо; ошибки конкретного продукта не превращаются автоматически в глобальный запрет.
