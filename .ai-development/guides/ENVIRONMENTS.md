# Подготовка среды, проверки и доставки

Это работа management и developer при запуске продукта. Цель — получить воспроизводимую разработку, проверку и доступный владельцу результат. Наличие документов или файла workflow само по себе не подтверждает готовность среды. Общий стандарт не выбирает стек за продукт и не выдаёт разрешения на рабочий сервер/платные сервисы.

## Единый порядок подготовки

1. Выбрать техническую основу по требованиям и ограничениям. Для существующего продукта использовать его рабочие команды и CI. Сохранить версии среды и lock-файлы; установка должна воспроизводиться в чистом окружении.
2. Подготовить одну команду проверки: обычно `bash scripts/verify.sh`, либо уже существующий эквивалент. Скрипт с `set -euo pipefail` устанавливает зависимости из зафиксированных версий и запускает применимые проверки/сборку. Внутри используются настоящие команды стека; пустой скрипт, `echo success`, подавление ошибки и тесты без проверяемых утверждений неприемлемы. Доступ к рабочим секретам и платным API для обычного CI не нужен.
3. Настроить CI на PR и целевую ветку. [templates/CI.yml](../templates/CI.yml) — готовая общая оболочка вызова `scripts/verify.sh`: скопировать в `.github/workflows/verify.yml` после подготовки команды. При существующем CI дополнить его вместо второго одинакового workflow. Для другого имени ветки, ОС/среды или команды адаптировать оболочку. Зафиксировать обязательные jobs и убедиться, что они реально запускались и выявляют известную ошибку. Проверка не должна быть skipped/neutral вместо успеха.
4. Подготовить тестовые данные и способ показать результат с телефона. Привязать демонстрацию к коммиту/сборке. Достаточно одного общего тестового окружения с последовательным обновлением; отдельное окружение для каждого PR не обязательно. Доступ к приватной демонстрации дать штатным способом, без публикации секретов.
5. Подготовить версионируемый артефакт, команду выпуска, проверку запущенной версии и восстановления по [RELEASE](RELEASE.md). Сначала проверить на безопасной тестовой среде или локальном аналоге то, что можно проверить без production. Не выдавать подготовку команды за состоявшийся выпуск.
6. Сохранить реальные команды и порядок в RUNBOOK, ссылки/возможности — в PROJECT. Зафиксировать фактические результаты и оставшиеся ограничения. До основной реализации закрыть зависимости, необходимые для проверки её результата; владельцу передавать только существенный выбор или действие, которое недоступно агентам.

## Применение к типам продукта

| Тип | Проверка в среде | Демонстрация владельцу | Доставка |
| --- | --- | --- | --- |
| Веб-сервис / Mini App | Зависимости, проверки кода, тесты, сборка, тестовая БД/интеграции | HTTPS-стенд; Mini App дополнительно открыть в реальном Telegram | Образ/пакет с неизменяемой версией, миграции, проверка приложения и фоновых компонентов |
| Telegram-бот | Обработчики, права, повторы/ошибки, тестовый транспорт и доступная реальная интеграция | Отдельный тестовый бот/чат и несколько целевых действий | Версионируемый процесс/образ; без второго конкурирующего потребителя тех же событий |
| Мобильное приложение | Сборка целевой платформы, тесты, применимый эмулятор/устройство; iOS — соответствующая macOS-среда | Устанавливаемая тестовая сборка или согласованный канал распространения | Подписанная сборка и отдельное подтверждение её доступности; загрузка в магазин ещё не выпуск |
| Библиотека / CLI | Тесты, сборка пакета, установка и вызов в чистом окружении | Пакет и понятный воспроизводимый пример | Версия пакета/бинарника с проверкой опубликованного артефакта |

Шаблон CI не создаёт приложение, тестовый стенд или учётные записи. Их настройка выполняется агентами под выбранный продукт. Шаблонные поля будущего продукта заполняются после выбора стека, до зависимой работы; владельцу не предлагается самостоятельно собирать инфраструктуру по регламенту.

## Работа при недоступной автоматизации

Паспорт отдельно указывает, настроены ли запуск разработчика, получение результата, продолжение управления и доставка. По умолчанию рабочий маршрут использует GitHub для материалов, готовое ручное поручение для недоступного запуска и ручной чат Claude с телефона. Отсутствие фонового обработчика не мешает продолжению по короткому сообщению владельца.

Если автоматизация подключена, она хранит идентификатор задачи/запуска, предотвращает повторный запуск той же работы и параллельные изменения одной ветки, проверяет актуальную версию перед действием и останавливается при новом существенном решении или исчерпании разрешённых ресурсов. После двух циклов исправлений без продвижения management пересматривает причину. Нельзя молча заменять недоступную подписку платным API или автоматически включать отложенный Claude Action.

Автоматический выпуск используется только в пределах выданной политики. При уже разрешённом выпуске новый запрос согласия не нужен. Если владелец выпускает вручную по своему выбору/доступам, он получает одну готовую команду с ожидаемым результатом и восстановлением; техническую подготовку полностью выполняет агент.
