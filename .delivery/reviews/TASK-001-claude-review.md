## Что подтверждено чтением кода

- **Игровая математика.** Формулы крафта `(s1+s2+s3+1)/2` и характеристик `(L·(100+P)+99)/100` верны для положительных целых. Округление выполняется один раз. Все 20 цен совпадают с таблицей PRODUCT.md. Нельзя получить 7.0 или смешать типы и уровни.
- **Инвариант экипировки.** Ограничение «выбранных ненадетых не больше имеющихся ненадетых» гарантирует, что после крафта надето не больше, чем есть. Группа с нулевым количеством удаляется только вместе с нулевой экипировкой.
- **Отмена.** Работает строго в порядке LIFO. Между крафтом и его отменой рабочие группы меняют только более поздние крафты, которые отменяются раньше. Поэтому восстановленная экипировка всегда согласована с количеством. Сброс очищает историю.
- **Транзакции.** Каждая команда выполняется в одной IMMEDIATE-транзакции. Проверка размера выбора (`SELECT_THREE`) идёт после записи, но откатывается вместе с ней. Это покрыто тестом.
- **Идемпотентность.** Повтор возвращается до проверки ревизии. Ключи разделены по владельцу. Тот же ключ с другим содержимым — 409 `KEY_REUSED`.
- **Владелец данных.** Берётся только из сессии. Поле `owner` в теле отклоняется. Чужая группа — 404, чужой эксперимент — 409.
- **Mini App.** Алгоритм HMAC (`WebAppData` → токен бота), запрет дублирующихся полей, сравнение за постоянное время, границы −300/+30 секунд.
- **OIDC.** Связь аккаунтов по claim `id`, а не `sub`, верна: документация Telegram показывает в ID-токене разные значения `sub` и `id`, а `id` возвращается в scope `profile`. Эндпоинты и Basic-аутентификация на токен-эндпоинте совпадают с discovery.
- **Сессии, CSRF, заголовки, образ.** Ротация сессии, CSRF и Origin, cookie-флаги, CSP. Образ работает без root, SHA проверяется при сборке, seed- и тестовых эндпоинтов нет.

## Подтверждённые дефекты (неблокирующие)

### D1. Допуск +30 с для `iat` в OIDC не работает

- **Серьёзность:** средняя.
- **Место:** `apps/server/src/auth.ts`, функция `oidcIdentity`.
- **Причина.** Вызывается `jwtVerify(..., {maxTokenAge:'1h', clockTolerance:0})`. При заданном `maxTokenAge` библиотека jose отклоняет токен, если его возраст меньше −tolerance. Это видно в исходнике jose: ошибка `"iat" claim timestamp check failed (it should be in the past)`. С `clockTolerance:0` отклоняется любой `iat` даже на секунду в будущем. Собственная проверка `payload.iat <= now+30` после этого уже не срабатывает.
- **Воспроизведение.** Подписать фикстуру с `iat = now+5` и вызвать `oidcIdentity`.
  - Ожидается по замыслу кода: токен принят.
  - Фактически: исключение jose, затем `LOGIN_FAILED`.
- **Влияние.** Если часы Telegram хоть немного опережают сервер, реальные входы через сайт будут периодически отказывать. Безопасность не страдает: система отказывает в доступе, а не пропускает.
- **Тесты.** Есть только проверка отказа для `iat = now+60`. Проверки, что `+5…+30` принимается, нет.
- **Исправление.** `clockTolerance: 30` (или иная согласованная величина) и тест на границы +30 и +31.

### D2. Ошибки клиента от Fastify превращаются в 500 `SERVER_ERROR`

- **Серьёзность:** низкая.
- **Место:** `apps/server/src/app.ts`, `setErrorHandler`.
- **Причина.** Сохраняются только `DomainError` и 413, всё остальное становится 500.
- **Воспроизведение.** Сессия и CSRF валидны, затем `POST /api/commands`:
  - с `content-type: application/json` и телом `{` — Fastify выдаёт 400 `FST_ERR_CTP_INVALID_JSON_BODY`, клиент получает 500;
  - с `content-type: text/plain` — 415, клиент тоже получает 500.
- **Влияние.** Нарушается контракт RUNBOOK («валидация — 400»). Клиент и мониторинг примут ошибку клиента за сбой сохранения. Данные не меняются.
- **Исправление.** Пропускать коды `e.statusCode` из диапазона 4xx с общим кодом ошибки и добавить тест.

## Гипотезы (не доказаны, нужна проверка)

### H1. Обязательный `nonce` может сломать весь реальный вход через сайт

- **Риск:** высокий.
- В ручном OIDC-потоке Telegram документирует параметры авторизации без `nonce`. `nonce` описан только для JS-библиотеки (`InitOptions`).
- В discovery `claims_supported` нет ни `nonce`, ни `id`.
- Код требует claim `nonce` (`requiredClaims` и строгое сравнение). Если Telegram не возвращает `nonce` в code flow, отказывать будет каждый вход.
- PKCE и state, привязанный к сессии, защищают и без nonce.
- **Как проверить:** первый живой вход на тестовом боте.
- **Решение по политике** (nonce обязателен или проверяется только при наличии) — за management. Это пересмотр решения из TECHNICAL, поэтому reviewer самостоятельно не предлагает его менять.

### H2. Неограниченная длина чисел может блокировать весь сервер

- **Риск:** средний.
- `integer()` принимает строки цифр любой длины в пределах 1 MiB тела. Драйвер синхронный, сервер однопроцессный.
- Диагностический замер на Node 22, отдельный скрипт: число из 1 млн цифр — разбор около 76 мс, `toString` результата около 320 мс. Каждая команда и `/api/state` пересчитывают характеристики, а результат пишется в `commands`.
- Значит, один авторизованный пользователь, скорее всего, может задерживать ответы всем остальным на сотни миллисекунд на каждый запрос.
- Технический предел длины записи — не игровой максимум. TECHNICAL прямо допускает технические пределы.
- **Как проверить:** замер на Node 24.22.1 и целевом размере хоста. Затем management решает, вводить ли предел длины десятичной записи.

### H3. Строгий список параметров callback

- **Риск:** низкий.
- `keys(q,['code','state'])` в `/auth/oidc/callback` отклоняет любой дополнительный параметр. Например, `error` при отказе пользователя или `iss` по RFC 9207.
- В таком случае пользователь увидит сырой JSON с 400 вместо понятного сообщения.
- **Как проверить:** живой вход, в том числе с отказом пользователя. Обработка сейчас не задокументирована.

## Достаточность проверок (неблокирующие замечания)

- **Конкурентность в тестах условная.** better-sqlite3 синхронный, поэтому `Promise.all` и `Promise.allSettled` выполняют команды последовательно. Результат «1 успех / 9 конфликтов» проверяет обработку устаревшей ревизии, а не борьбу за блокировку. При одном процессе это корректно. Межпроцессный сценарий (backup, fixture в smoke) тестами не нагружается. Достаточно было бы worker_threads с отдельными соединениями.
- **Замер вставки занижает задержку.** `scripts/measure.ts` вставляет 10 000 групп внутри одной внешней транзакции. Реальные 10 000 HTTP-команд — это 10 000 commit с синхронизацией WAL, плюс 10 000 строк в `commands`. Цифру «insert 2727 мс» нельзя переносить на сценарий ввода пользователем.
- **Восстановление проверено на уровне Store.** Копия открывается через Store (`/data/snapshot.sqlite`), но сервер на восстановленном volume не запускается. RUNBOOK описывает запуск образа на новом volume, smoke этого не делает. Критерий E по смыслу выполнен, путь эксплуатации подтверждён не полностью.

## Эксплуатационные замечания (вне критериев, для следующих задач)

- **Рост `sessions` без авторизации.** Анонимный `GET /auth/oidc/start` создаёт строку сессии на 12 часов без ограничения частоты.
- **Выход через навигацию.** Переход верхнего уровня на `/auth/oidc/start` разлогинивает текущую сессию (вынужденный выход, низкий риск).
- **Таблица `commands` растёт бесконечно.** В каждой строке хранится полная сводка, очистки нет, даже при сбросе.
- **`logger:false` отключает и диагностику.** Причины 500 нигде не видны. Задание требовало не писать секреты в логи, а не отказываться от логов совсем.
- **Права файла бэкапа.** `backup.ts` создаёт копию с правами по umask. RUNBOOK требует ограниченные права, код этого не обеспечивает. В копии лежат CSRF-токены и HMAC сессий.
