## Причина и граница исправления

Владелец подтвердил успешный image proof и запуск app из прежнего R6 kit fbe, затем отказ baseline ingress validation до plan.json. Безопасная сводка установила категории data/log_writer, open/read, read_only=true и validate_started=true. Настоящий Caddyfile, raw diagnostics и данные владельца reviewer не получал. Свой synthetic native сценарий ниже воспроизводит этот класс отказа: Caddy `validate` открывает file writer даже при проверке без запуска серверов, а исходный helper принудительно монтирует `/data` RO.

Исправленный helper сначала выполняет `adapt` исходного Caddyfile с фактическими image/env и исходными RO mounts. Затем нативный `validate --config -` получает через stdin копию полного adapted JSON. Только `logging.logs.*.writer.output=file` меняет `filename` на цель в отдельном tmpfs1MiB; одинаковый исходный filename сохраняет одну общую временную цель. Остальные writer options/encoder/modules/credentials/certificate paths остаются в конфиге. Неизвестные writers не удаляются и не обходятся. Deep-copy сохраняет как adapted JSON, так и исходные определения Compose volumes; возвращается оригинальный adapted JSON для TLS equality check.

Проверка не копирует `/data`, не открывает рабочие mounts RW, не меняет пользователя, сети, исходный Caddyfile или общий compose. Tmpfs уникален, ephemeral, mode1777, ограничен1048576bytes, удаляется с `run --rm`; validation network=none и без опубликованных портов. JSON не передаётся через argv/публичный вывод. Ошибка даёт фиксированную фазу без raw config/stderr; stderr остаётся в private ingress diagnostics. Существующие image/env/process/ordered-source/drift guards, TLS equality, stage-before-plan и apply/rollback не ослаблены.
