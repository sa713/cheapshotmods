# Выпуск и сопровождение

Применять вместе с паспортом продукта и его runbook. Этот документ не выдаёт разрешение на слияние, публикацию, расходы или доступ к production.

## До выпуска

1. Установить принятый HEAD, результат интеграции с целевой веткой, актуальность проверок и применимое пользовательское принятие. Если merge создал новый коммит, проверить связность результата; артефакт связывается с фактически собранным коммитом.
2. Выбрать неизменяемую версию артефакта: digest образа, коммит/версия пакета или подписанная сборка. Не полагаться только на изменяемую метку latest или Git HEAD в каталоге сервера.
3. Проверить конфигурацию и секреты по наличию/метаданным, не выводя значения. Убедиться в доступности ресурсов и совместимости зависимостей.
4. Для затронутых данных предусмотреть свежую копию и проверяемый способ восстановления. Откат приложения не обязательно откатывает схему данных: выбрать совместимую миграцию, forward-fix или восстановление с явно описанными последствиями.
5. Подготовить конкретные команды/скрипт, ожидаемый вывод, критерии успеха/остановки, восстановление и ответственного. Скрипт не должен продолжать опасные шаги после ошибки; повторный запуск должен быть безопасен либо явно запрещён.
6. Установить действующее разрешение. Если его нет — закончить обратимую подготовку и запросить решение о конкретном выпуске.

## Выполнение и подтверждение

Выполнять только разрешённые шаги. При ручном выпуске владелец получает готовую команду и возвращает вывод; агент не заявляет, что сам заходил на сервер. Для действий через интеграцию записать фактический результат инструмента.

Проверить после выпуска:

- запущена/доступна именно нужная версия; для app/worker/bot и других компонентов — согласованность;
- readiness/health, нужные зависимости и отсутствие новых критичных ошибок;
- целевой пользовательский сценарий в целевом окружении;
- сохранность ранее существовавших данных, если изменение могло на них повлиять;
- восстановление предусмотрено и его материалы доступны.

HTTP 200, успешный git pull, сборка контейнера или изменение документа STATE по отдельности не подтверждают выпуск. Не закрывать функциональную задачу, если проверена только локальная версия. Для магазина приложений различать загруженную сборку, рассмотрение и фактическую доступность; для пакета — собранный файл и опубликованную версию.

## При неудаче

Остановить следующие изменения, сохранить диагностический вывод без секретов, определить влияние. В рамках полномочий восстановить последнюю рабочую версию/данные согласно runbook. Если восстановление необратимо или не разрешено, подготовить конкретное решение владельцу. Не запускать случайные миграции/очистки ради устранения симптома.

Зафиксировать delivery=failed, версию, симптомы, выполненные действия и текущую работоспособность. Создать связанную задачу исправления; не стирать факт неудачного выпуска. После восстановления проверить рабочую систему и закрыть инцидент по фактам.

## Сопровождение

В runbook определить: диагностику, резервирование и проверку восстановления, обновление зависимостей, ротацию секретов при необходимости, ресурсные и стоимостные ограничения, прекращение эксплуатации и удаление данных по решению владельца. Мониторинг/расписание считается настроенным только после проверки механизма. Для небольшого продукта достаточно короткого применимого раздела, без фиктивных SLA и круглосуточного дежурства.
