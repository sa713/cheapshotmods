### A. Воспроизводимость и реальные проверки

Защиту ветки не считать включённой только из-за наличия YAML. Если Actions/сеть недоступны — зафиксировать конкретную ошибку и непрошедший критерий, не помечать задачу принятой.

### B. Точные правила и отрицательные сценарии

Покрыть все цены и переходы 1.0→6.0, четыре типа и требования PRODUCT.md, в том числе:

- Уровень 200 без модов: D = H = 200; 🅾 +10, 💢 +8 и 🧿 +8: D = 252, H = 200. Уровень 101 с одним 💢 +8: D = 110; с двумя: D = 118. Уровень 200 со 100 🅾 +10: D = 2200. Надевание 101-го отклоняется без изменения состояния.
- Крафт 🅾 10/10/10 → 15, 15/15/15 → 23, 10/11/12 → 17; цепочки до 6.0 и таблица всех 20 цен проверяются по PRODUCT.md. 💚 3.0 стоит 162, 🧿 2.0 — 72, 💢 2.0 — 66. Не объединять разные типы/уровни, не получать 7.0, не использовать недостающие/повторно выбранные экземпляры.
- В исходном наборе шесть 🅾 1.0 по 10: крафт в рабочем наборе оставляет три исходных и один 🅾 2.0 по 15, расход 84, исходный набор по-прежнему шесть. Второй крафт даёт расход 168. Отмена второго возвращает расход 84, повторная отмена — 0 и исходную рабочую шестёрку.
- Крафт надетых экземпляров снимает выбранные, результат не надевается автоматически. Если затем надеть результат/изменить экипировку, отмена удаляет результат и возвращает экипировку непосредственно перед крафтом. Текущий уровень игрока сохраняется.
- Правка исходного набора не меняет уже начатый эксперимент. Сброс берёт актуальный исходный набор, очищает историю/экипировку/расход и сохраняет текущий уровень игрока. Пустой исходный набор допустим; при пустой экипировке D=H=L.
- Для 1.0 🅾 допустимы 10/11/12, 💢/🧿 — 8; для 2.0–6.0 принимается фактическое положительное целое. 💚 — положительное целое. Дробь, ноль, отрицательное, неверный тип/уровень и некорректный формат отвергаются без изменения данных. Большие положительные целые не округляются через Number.
- Проверить уровень/параметр/количество больше `9007199254740991`, например `9007199254740993`: строки/BigInt проходят через API, БД и повторное чтение без изменения значения. Точное тестовое ожидание считать независимой целочисленной формулой/константой, не вызовом тестируемой функции.

### C. Транзакции, повторы и изоляция

- Реальная SQLite, не только mock: сохранить исходный набор/уровень/экипировку/крафт/расход, перезапустить процесс/открыть БД заново → те же данные, доступна отмена после перезапуска.
- Потерять HTTP-ответ после commit крафта, повторить ту же команду с тем же key и исходной ревизией → вернуть прежний результат, один крафт, одно списание, без ложного конфликта. Повторить после перезапуска → то же. Тот же key с другим payload отклонить без изменений.
- Два разных действия одного игрока с одной ожидаемой ревизией выполняются конкурентно → ровно одно успешно, второе409, ревизия и расход соответствуют одному действию. Новая команда после сброса не использует состояние старого эксперимента.
- Инъекция ошибки между изменением модов и записью расхода/истории → транзакция откатывает весь шаг. Невалидные команды и сбой БД не возвращают успешное сохранение.
- Два тестовых Telegram ID: подмена ID в URL/теле, ID чужой группы/эксперимента и неверная сессия не позволяют читать/менять чужие данные; владельца всегда берёт сервер из сессии. Повтор команды одного пользователя не возвращает результат другого.
- Сессии имеют серверную инвалидизацию; изменяющие cookie-запросы требуют CSRF/Origin-защиту. Секреты, cookies, сырые ID tokens и initData не выводятся в логи/ответы ошибок. Production не содержит незащищённого test-login, заголовка доверенного пользователя или встроенного тестового ключа.

### D. Вход Telegram на проверяемых фикстурах

- OIDC: валидный подписанный ID token принят только при правильных issuer/audience/сроках/nonce. Неверная подпись, issuer, audience, просрочка/неверный nonce, повтор state/code и неправильный PKCE отклоняются; token exchange/доверенный JWKS мокируются на границе транспорта, реальная криптография остаётся включённой.
- Запрос scopes ограничен `openid profile`; нет запроса телефона или bot_access. `state`, `nonce` и PKCE verifier одноразовые, привязаны к начинающей вход сессии; session ID обновляется после входа.
- Mini App: корректно подписанное initData принимается, подмена user, неверный hash, дублирующиеся критичные поля, отсутствие user/подписи и устаревший auth_date отвергаются. Политика — 300 секунд и не более 30 секунд в будущем; на границах есть тесты. Не доверять `initDataUnsafe`.
- Одна фикстура содержит OIDC `sub`, намеренно отличный от `id`; валидный profile `id` совпадает с Mini App `user.id` → оба пути открывают один агрегат игрока. Другой user.id открывает отдельный агрегат. Только `sub` без подтверждённого Telegram `id` не создаёт неверную привязку.
- При отсутствии Telegram-конфигурации личные данные недоступны; экран сообщает о недоступности входа, а не имитирует авторизацию. В отчёте явно указано, что реальные BotFather, браузерный Telegram Login и Telegram WebView не проверены.

### E. Артефакт, ёмкость и восстановление

- Docker image собирается в CI, запускается без root где это совместимо с volume; помечен полным исходным Git SHA. `/version` выдаёт именно эту версию, `/health` проверяет доступность SQLite. Нет секретов/production data в образе.
- На тестовом volume после сохранения данных контейнер удаляется/создаётся заново с тем же volume → состояние восстановлено, миграция повторно безопасна. CI smoke действительно выполняет этот сценарий.
- Выполнить backup/restore согласованной копии SQLite с WAL в новый volume; сравнить данные и возможность последующей отмены/крафта. Не восстанавливать поверх production. Записать точные команды и результат.
- Данные: 10 000 разных групп, отдельно группа с 1 000 000 одинаковых экземпляров, 10 конкурентных команд и большой точный integer из B. Добавление огромного количества одинаковых модов не разворачивает экземпляры в объекты/строки. Записать память, размер БД, задержки и характеристики среды; 100 — только лимит экипировки. Выборка не становится максимумом инвентаря.
- При ошибке лимита запроса/ресурса данные не повреждаются и API возвращает понятную ошибку. Если измерения превышают планировочный ориентир 1 vCPU / 512 MiB либо выбранная SQLite/Node основа не справляется, передать факты management и предлагаемое решение; не скрывать провал ограничением игрового инвентаря.

- **D2 — подтверждён в части классификации 4xx, пример уточнён.** Management исполнил точное выражение текущего error handler: Fastify statusCode 400/401/403/415 становятся 500, 413 сохраняется. Для проверки неподдерживаемого типа использовать application/xml. Источники — код и официальная документация парсеров, ссылки ниже.
- **H1 — остаётся гипотезой и обязательной проверкой живого входа.** Отсутствие nonce/id в discovery не доказывает отсутствие claims в ID token. Тестового бота/разрешённого HTTPS-стенда нет. До реального успешного code flow совместимость не подтверждена; если провайдер действительно не возвращает nonce, management принимает отдельное решение на основании фактического ответа/официальных данных.
