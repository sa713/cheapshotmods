## Оценка F1–F6

### F1 — допуск будущего `iat` в OIDC — достаточно

- **Код.** `auth.ts`, `oidcIdentity`. `maxTokenAge` убран из `jwtVerify`, `clockTolerance: 0` и `currentDate` сохранены. Дальше собственная проверка: `iat ∈ [now−3600, now+30]` включительно, `exp > now`, `exp > iat`, `nonce` совпадает.
- **Почему это корректно.** В jose проверка «iat должен быть в прошлом» живёт только в ветке `maxTokenAge`; без него jose проверяет лишь, что `iat` — число ([коммит jose](https://github.com/panva/jose/commit/96d85c70033d2249de41ed07d97ed6843c15eb2a)). `exp` и `nbf` jose проверяет строго при нулевом допуске. Значит, допуск +30 с не продлевает ни `exp`, ни `nbf`, а предельный возраст 1 час обеспечен нижней границей `iat`.
- **Сохранено.** Подпись, issuer, audience, `requiredClaims` (включая `nonce`, `id`), state, PKCE, защита от повтора кода.
- **Тесты.** Новый тест сначала воспроизводит D1 на закреплённой jose (с `maxTokenAge` будущий `iat` отклоняется). Затем проверяет −3600/0/+5/+30 — приняты, −3601/+31, `exp ≤ now`, `exp ≤ iat`, `nbf = now+1` — отклонены, `nbf = now` — принят. Этого достаточно для поручения.
- **Не исполнялось мной:** jose в моей среде нет. Исполнение — у Codex, management и CI.

### F2 — HTTP-коды ошибок — достаточно

- **Код.** `app.ts`, `setErrorHandler`. `DomainError` сохраняет свой код. Целочисленный `statusCode` 400–499 от Fastify сохраняется с публичным кодом: 413 → `REQUEST_TOO_LARGE`, 415 → `UNSUPPORTED_MEDIA_TYPE`, прочие 4xx → `INVALID_REQUEST`. Всё остальное — 500 `SERVER_ERROR` без деталей.
- **Утечек нет.** В ответ попадает только код, без сообщения, стека или тела. Перечислил все источники исключений в обработчиках: SQLite-ошибки и `JSON.parse` не несут `statusCode`, ошибки jose и transport ловятся в `callback`. Значит, внутренний сбой не может замаскироваться под 4xx.
- **text/plain.** Встроенный парсер возвращает строку, `record()` отклоняет её как 400 `INVALID_COMMAND`. Это соответствует уточнению management.
- **Тест.** Через `inject` с валидной сессией, Origin и CSRF: три случая, сводка и число `commands` не меняются. Существующие проверки 401/403/404/409/413/500 сохранены. RUNBOOK описывает коды так же, как код.
- **Наблюдение, не дефект.** Тело разбирается до проверки сессии, поэтому битый JSON без сессии получает 400, а не 401. Состояние не меняется, утечки нет.
- **Не исполнялось мной:** Fastify в моей среде нет.

### F3 — ограничение длины чисел — достаточно

- **Код.** `inputInteger` проверяет тип и длину ≤ 128 до регулярного выражения и `BigInt`. В `Store.command` все недоверенные числовые поля проверяются до `canonical()` и до транзакции: `revision`, `value` и `quantity` в `level`/`original.put`, `quantity` и `worn` в `equip`/`craft`. Отказ не создаёт даже строку игрока.
- **Перечень мест разбора.** Прошёл все `integer()` и `BigInt()` в сервере и правилах. Оставшиеся вызовы работают только по сохранённым или производным данным либо по данным, подписанным Telegram (`id`, `auth_date` после проверки HMAC или подписи).
- **Производные значения не упираются в лимит.** Клиент никогда не передаёт параметр мода обратно: `equip` и `craft` принимают только `id`, `quantity`, `worn`. Рост ограничен: крафт даёт не больше ⌈3·max/2⌉, пять крафтов умножают максимум примерно на 7,6. Значит, из 128-значного ввода получается не больше 129 цифр — ровно то, что проверяет регрессия.
- **Собственное исполнение** (заменяющая среда, см. ниже):
  - 1 000 000 цифр → `INTEGER_TOO_LONG` за 0,1 мс, все четыре таблицы без изменений;
  - 129 цифр в `revision`, `value`, `quantity` (put/equip/craft), `worn`, а также при правке существующей группы → `INTEGER_TOO_LONG`, таблицы без изменений;
  - 128 цифр принимаются; повтор принятой команды с тем же ключом возвращает идентичный результат; другой игрок продолжает работать;
  - регрессия 129-значных модов (`store.test.ts`) прошла: чтение, экипировка, следующий крафт, undo, reset.
- **Побочный эффект, приемлемый.** Порядок кодов ошибок изменился: `INTEGER_TOO_LONG` теперь возникает раньше `KEY_REUSED`, `GROUP_NOT_FOUND`, `EQUIPMENT_LIMIT`. Все варианты — отказ без изменения данных.

### F4 — backup/restore — достаточно, включая новое исправление trim

- **Создание копии.** `backup-file.ts`: `openSync(target, 'wx', 0o600)` — эксклюзивно, O_EXCL не следует по symlink. Затем `fchmodSync(0600)` до того, как SQLite откроет файл. Существующий файл и symlink не перезаписываются.
- **Очистка.** При ошибке удаляется путь, только если это тот же inode, иначе ничего. Ошибка очистки не теряет исходную причину.
- **Исправление trim — полное для этого класса.** И helper, и драйвер используют один и тот же `String.prototype.trim()` (`filename = filename.trim()` в приложенном `backup.js` драйвера). Отказ при `target !== target.trim()` до `openSync` устраняет расхождение между путём файловой системы и путём SQLite целиком, а не для отдельных символов.
- **Права служебных файлов.** Насколько мне известно, unix VFS SQLite создаёт `-journal` с правами файла БД, так что временный журнал копии тоже будет 0600. Сам я этого не проверял.
- **Smoke.** Тот же образ запускается на втором volume с восстановленной БД. Проверяются health, version, 401 без сессии, затем через синтетическую Mini App-сессию с CSRF — совпадение состояния и обоих наборов с ожидаемыми и undo/craft через HTTP. Свежая БД не могла бы совпасть (уровень 9007199254740993, расход 84). Добавлено ожидание готовности после пересоздания контейнера. Синтетический токен передаётся только одноразовому контейнеру, в образ не попадает.
- **Собственное исполнение.** `backup.test.ts` прошёл 2/2. Мутационная проверка:
  - убрал проверку trim → тест на псевдонимы падает;
  - вернул режим без `wx`/0600 → оба теста падают (ожидалось 0600, получено 0644).
  Регрессии действительно ловят оба исходных дефекта.
- **Остаточное ограничение, не дефект.** Между `openSync` и открытием файла SQLite есть окно: участник с правом записи в родительский каталог может подменить путь. RUNBOOK требует приватный каталог, что закрывает этот сценарий. Каталоги код не создаёт, поэтому требование «каталог 0700 при необходимости» сводится к инструкции RUNBOOK.

### F5 — межпотоковая конкуренция и методика замера — достаточно

## Неблокирующие замечания

### N1. Тесты зависят от заранее собранного `dist`

- **Серьёзность:** низкая, гигиена тестов.
- **Место.** `tests/fixtures/command-worker.mjs` импортирует `apps/server/dist/store.js`. `tests/backup.test.ts` запускает `apps/server/dist/backup.js`.
- **Условие.** `npm test` без предварительного `tsc -b`/`npm run build`, либо после правки `src` без пересборки.
- **Последствия.** На чистом checkout два теста падают с `ERR_MODULE_NOT_FOUND`. С устаревшим `dist` тесты молча проверяют старый код, при этом сама настройка и проверка конкурентного теста идут через `src`. В `verify.sh` порядок правильный (`typecheck` с `tsc -b` идёт до `npm test`), поэтому CI это не затрагивает.
- **Доказательство.** Удалил `dist` и запустил — 2 из 3 тестов упали с `Cannot find module …/dist/store.js` и `…/dist/backup.js`.
- **Исправление.** `pretest: tsc -b` в package.json, либо запуск worker и CLI через `--import tsx` по исходникам.

### N2. Probe pipefail не защищает настройку workflow от регрессии

- **Серьёзность:** низкая.
- **Место.** `scripts/check-measure-pipeline.sh` вызывает `bash … -e -o pipefail` с жёстко заданными флагами.
- **Последствия.** Probe проверяет семантику bash, а не конфигурацию `verify.yml`. Если удалить `defaults.run.shell: bash`, probe останется зелёным, а шаг замера снова будет скрывать сбой. Текущая конфигурация верна.
- **Исправление** (одно из двух): `set -o pipefail;` прямо в шаге замера, чтобы он не зависел от defaults, либо проверка в probe, что workflow действительно задаёт `shell: bash`.

### N3. Документы передачи: часовые пояса и исторические разделы

- **Серьёзность:** низкая, документация.

## Гипотеза (вне области F1–F6, существовала до этого цикла)

### G1. Тот же trim-псевдоним в конструкторе БД

- **Предположение.** Насколько я знаю, конструктор better-sqlite3 тоже обрезает имя файла. А `Store` вызывает `mkdirSync(dirname(path))` по необрезанному пути, и CLI backup проверяет `existsSync(source)` тоже по необрезанному.
- **Последствия, если подтвердится.** `DATABASE_PATH` или `SOURCE` с пробелами по краям молча откроет другой файл. Для backup CLI это копия не той БД, если существуют оба файла. Данные не портятся: источник только читается. Это ошибка конфигурации оператора.
- **Как проверить.** Прочитать `node_modules/better-sqlite3/lib/database.js` закреплённой версии (в пакет не входит) или создать `Store('x.sqlite ')` и посмотреть, какой файл открыт.
- **Исправление.** Тот же отказ при пробелах по краям в конструкторе `Store` и проверке конфигурации `main.ts`. Отдельной задачей, если подтвердится.
