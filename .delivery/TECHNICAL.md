## Вывод и порядок реализации

Продукт реализуем как один веб-сервис с постоянным хранилищем и двумя входами Telegram. Игровые формулы, цены и поведение эксперимента достаточно определены; повторный продуктовый сбор не требуется. Правила игры берутся из PRODUCT.md и остаются предоставленной владельцем моделью будущей системы; проверка внешней публикации игры не входит в задачу.

Следующая готовая задача — техническая основа и проверка точных расчётов, транзакций и входа на фикстурах. Это подготовка конечного продукта, не сокращение его требований. Полный мобильный пользовательский интерфейс и живой Telegram проверяются после подготовки среды и получения недостающих доступов. Основная реализация не объявляется готовой поверх неизвестного размещения.

## Выбранная основа

- Один репозиторий, npm workspaces: общий TypeScript-модуль правил/контрактов, сервер Fastify 5, клиент React + Vite. Node.js 24 LTS одинаковой проверенной версии для разработки, CI и контейнера; exact-версии инструментов/зависимостей и lock-файл закрепляет TASK-001.
- SQLite через `better-sqlite3`, WAL, foreign keys, явные транзакции и миграции. Один экземпляр сервера с локальным постоянным volume; SQLite-файл не размещать на сетевом диске. Вторая БД/Redis/отдельный worker не нужны для принятого объёма. Переход к нескольким экземплярам и большой аудитории потребует отдельного решения.
- Выбор SQLite соответствует локальным атомарным действиям игрока. Это технический вывод, не подтверждённая производительность. Масштаб аудитории неизвестен; TASK-001 измеряет ёмкость, не обещает SLA.
- `better-sqlite3` выбран вместо release-candidate `node:sqlite` в проверенной Node 24.22.1. Его native-сборку/совместимость с точной Node-версией нужно подтвердить в чистом Linux CI и контейнере. Новые зависимости проверять по их первичным лицензиям; MIT у базовых React/Vite/Fastify/драйвера и TypeScript Apache-2.0 не требуют покупки, но не являются аудитом всех транзитивных пакетов.
- Один origin для UI и API снижает сложность cookie/CORS. Контейнер собирает frontend заранее, runtime обслуживает готовую статику и API. Версия артефакта — полный Git SHA; секреты передаются только во время запуска.

## Модель данных и вычислений

- Исходный инвентарь и рабочий набор — отдельные агрегаты; один текущий эксперимент на Telegram ID. Редактирование исходного набора не меняет эксперимент до сброса. Эксперимент хранит собственную копию данных, не живые ссылки на исходные изменяемые строки.
- Одинаковые моды хранить партиями/группами с количеством. Не выделять миллион строк/объектов для миллиона одинаковых модов. Выбор трёх отдельных экземпляров и надетой части должен быть однозначным; допустима эквивалентная модель количества с явным учётом экипировки и происхождения. Лимит 100 проверяется по экипировке, не по инвентарю.
- Все игровые числа — положительные целые; проценты и результаты крафта тоже целые. Для математических значений использовать BigInt и десятичные строки в JSON/хранилище; не терять точность через JS Number/SQL REAL или 64-битный предел количества. Типы/уровни мода и ограниченное число надетых экземпляров можно хранить как малые целые.
- Точные формулы для положительных целых: `craft = (s1+s2+s3+1)/2`; `stat = (L*(100+P)+99)/100`, где `/` — целочисленное деление. Прибавки отдельно не округлять. Цены — строго таблица PRODUCT.md, включая 💚 3.0 = 162 и отличающиеся 💢/🧿.
- Технический предел размера HTTP-запроса/ресурса должен давать понятную ошибку без изменения данных. Он не превращается в новый игровой максимум уровня, HP или инвентаря; большие инвентари передаются/отображаются постранично. Не заявлять физически бесконечную ёмкость.
- Отмена хранит обратимые изменения крафта и экипировку непосредственно перед ним. Полный снимок всего инвентаря на каждый крафт не нужен. Повторная отмена восстанавливает шаги по порядку, сохраняя текущий уровень игрока. Сброс использует актуальный исходный набор, очищает историю/экипировку/расход и сохраняет уровень.

## Согласованность и сохранение

- Сервер — источник истины; клиент отправляет команду, а не доверенный итоговый урон/расход/произвольный слепок данных.
- Каждая изменяющая команда содержит idempotency key и ожидаемую ревизию агрегата игрока. Авторизованный Telegram ID выводится из сессии, не принимается как доказательство из тела/URL.
- В одной SQLite-транзакции валидируются доступные моды/ревизия, изменяется состояние, записываются история, расход и результат команды. Сбой до commit не оставляет частичных результатов.
- Для повтора с тем же key и тем же содержанием вернуть зафиксированный результат до проверки устаревшей ревизии; иначе потеря ответа превратит успешный повтор в ложный конфликт. Тот же key с другим содержанием отклонить. Пространство ключей ограничено владельцем/командой и учитывает сброс эксперимента.
- Две разные команды на одной ревизии: одна успешна, вторая получает конфликт 409 без изменения данных. Клиент сообщает о конфликте и предлагает загрузить сохранённое состояние. Не перезаписывать его автоматически.
- Автосохранение подтверждается только после commit. Потеря ответа не равна неуспешной операции: показывается неопределённый/несохранённый статус и возможен безопасный повтор с тем же key.

## Telegram: два входа и одна личность

Проверено по официальной документации 2026-11-05; ссылки ниже. Не использовать устаревший iframe Login Widget как безусловный стартовый выбор.

- Сайт: Telegram OIDC Authorization Code Flow, PKCE S256, server-side state/nonce и проверка ID token по доверенному JWKS. Проверять подпись, issuer, audience, exp/iat/nonce; redirect URI только зарегистрированный. Scope `openid profile`; телефон и право отправлять сообщения не запрашивать.
- **Ключ общей учётной записи — Telegram user ID.** В документированном OIDC токене `sub` и `id` различаются; брать подтверждённый claim `id` из profile. Для Mini App это проверенный `user.id`. Не связывать аккаунты по username, имени, фотографии или равенству `sub`/user.id.
- Mini App: передать сырой `Telegram.WebApp.initData` серверу, проверить подпись по официальному алгоритму и свежесть `auth_date`; `initDataUnsafe` не является доказательством личности. Начальная политика свежести — 5 минут, допустимый уход часов в будущее — 30 секунд; после проверки выдаётся собственная серверная сессия. Токен бота не попадает в клиент.
- Серверные сессии: случайный непрозрачный идентификатор, безопасная HttpOnly cookie для одного origin, Secure в HTTPS, CSRF-защита изменяющих действий и проверка Origin. Проверить работу cookie в реальном Telegram WebView отдельно; локальный браузер этого не доказывает. Таймаут/выход инвалидирует сессию на сервере.
- Существующие Telegram-боты других продуктов не использовать. Достаточно выделенного бота с настроенным Main Mini App/menu button: рассылки, polling и обработка чатов не нужны для калькулятора.
- Без настоящего бота и зарегистрированного HTTPS URL можно проверить криптографию, протоколы и изоляцию на тестовых данных; нельзя подтвердить реальный вход, общий аккаунт двух реальных клиентов и открытие Mini App.

## Доставка, ресурсы и незакрытые условия

- Контейнер приложения + постоянный volume SQLite; HTTPS предоставляет согласованный reverse proxy. Ни внешний хостинг, ни новый VPS не создаются текущим поручением. Конфигурация контейнера/compose до назначения хоста проверяется локально и в CI, с сохранением БД при пересоздании контейнера.
- Первая нагрузочная выборка: 10 000 различных групп одного игрока, группа с 1 000 000 одинаковых модов и 10 одновременно выполняемых команд разных/одного игрока. Это проверочная выборка, не продуктовый максимум. Измерить память, размер БД, время загрузки/действия и восстановление; записать характеристики машины и методику. Отдельно проверить число выше `Number.MAX_SAFE_INTEGER` без разворачивания количества.
- Предварительный ориентир приложения — 1 vCPU и 512 MiB RAM, сборка выполняется вне runtime. Это гипотеза для измерения TASK-001; фактический сервер и запас диска/бэкапов не назначены. При превышении сообщить измерение и причину, не подменять её выдуманным лимитом в 100 модов.
- Нужны решения до живого стенда: выделенный бот и секреты; HTTPS-адрес/его регистрация; где хранится БД, резервные копии и кто предоставляет доступ; разрешение размещения и ресурсный бюджет. Это блокеры живой интеграции и доставки, не локального TASK-001.
- Полный продукт потребует мобильных сценариев S-01–S-06, доступной с телефона версии, двух реальных Telegram-пользователей для изоляции и проверки восстановления. TASK-001 не заменяет эту приёмку.


## Уточнения по ревью — решение management от 2026-11-05

- **Ресурсный предел ввода:** не более 128 десятичных цифр в одном недоверенном числовом поле API команды, до преобразования в BigInt; превышение → 400 INTEGER_TOO_LONG без изменения состояния. Это технический размер поля, не утверждение о максимуме в игре и не ограничение общего числа экземпляров/групп. Числа больше JS safe integer остаются поддержаны точно.
- Лимит относится к исходному вводу и клиентским числовым полям, не к корректным внутренним результатам. Сгенерированный крафтом параметр может вырасти до 129 цифр и должен сохраняться, читаться, экипироваться, участвовать в дальнейших разрешённых крафтах и отменяться. Точность статистики/расхода сохраняется. Механически ограничивать общий helper integer так, чтобы он ломал валидный сохранённый результат, нельзя.
- Основание: одиночный запуск текущего rules.stats на Work Node 24.22.1 с миллионом цифр занял 1485,1 мс; 128 цифр — 0,6 мс. HTTP-нагрузка и целевой хост этим замером не подтверждены. Ресурсный риск проверяется и устраняется в F3 TASK-001.
- **Политика OIDC времени:** iat ∈ [now−3600, now+30] секунд включительно, exp строго позже now и iat; nbf не ослабляется. Все проверки подписи/issuer/audience/state/nonce/PKCE/replay сохраняются. Возможное применение clockTolerance библиотеки не должно неявно продлевать exp или максимальный возраст.
- **Живой вход:** H1 о nonce остаётся неподтверждённой совместимостью code flow. До живого теста nonce обязателен. Зафиксировать успешный code flow, отказ пользователя, дополнительные параметры callback (включая iss при наличии), общий Telegram ID сайта/Mini App и cookie в WebView. Если nonce не приходит, решение принимает management по фактам; отсутствие claim в discovery само по себе не доказательство.
- **До внешнего размещения:** в следующей задаче закрыть частоту запуска входа/рост анонимных sessions, срок хранения commands с сохранением идемпотентности, обезличенную диагностику 500 и понятные ответы callback. Это условия будущей живой интеграции, не уже реализованные возможности. Текущий цикл ограничен F1–F6 [карточки TASK-001](tasks/TASK-001.md).

## Реализация эксплуатационных условий в TASK-002

Политики и команды определены в [RUNBOOK](RUNBOOK.md): лимитер 20/IP и 100/process в минуту с ограниченной памятью, анонимный flow 5 минут, очистка истёкших sessions/oidc_codes при старте и ежеминутно; результаты команд 30 дней с постоянными хеш-квитанциями вместо повторного применения старого key; обезличенные ошибки 500 и понятный callback. Миграция SQLite 1→2 транзакционная; rollback сохраняет старый image вместе с прежним volume, не открывает новую схему старым binary.

Клиент использует серверные ревизии, keyset pages по 100 и точные BigInt-правила. Размер страницы не ограничивает число модов. Экипировка до 100 возвращается со всеми параметрами отдельно, чтобы её управление не зависело от страницы инвентаря. Последовательность команд сериализуется в одном клиенте; неопределённая команда переживает reload в sessionStorage под account HMAC и повторяется без смены ключа. Ответ replay не применяется как актуальный snapshot: клиент перечитывает сервер.

Debian-комплект использует Docker image полного source SHA, закреплённые Node/Caddy digests, приватный literal env, постоянный отдельный volume и Caddy. Update закрывает ingress/останавливает app **до** согласованного snapshot, клонирует в новый volume и сохраняет предыдущую пару для rollback. Для rootless vfs сокращены слои Dockerfile: исходный многослойный cold build исчерпал 32 GiB среды, хотя CI с overlay завершил сборку. Сокращение слоёв меняет эффективность build cache, не состав runtime и не выполнение native install scripts. Конкретные результаты/ограничения фиксируются в TASK-002, это не наблюдение хоста владельца.
