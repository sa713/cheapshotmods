# Проверка качества

Проверка строится от требований к доказательствам. «Тесты прошли» без версии, команды и результата не является достаточным отчётом. Покрытие строк, количество тестов и согласие двух моделей не доказывают правильность продукта.

## Выбор глубины

| Риск | Минимальная достаточная проверка |
| --- | --- |
| Низкий | Проверка изменённого поведения/текста, сборка при необходимости, визуальная проверка интерфейса; отдельное ИИ-ревью не обязательно |
| Обычный | Целевые автоматические проверки, независимая сессия ревью, основной пользовательский сценарий и затронутые ошибки/границы |
| Повышенный | Всё применимое выше плюс негативные сценарии, разграничение прав, сохранность данных, совместимость и восстановление; существенные неопределённости не скрываются |

## Что проверять

1. **Смысл.** Правильно ли понята задача? Ключевые примеры и ожидаемые результаты определены до кода. Проверить ошибку самого задания относительно исходной потребности.
2. **Логика.** Правила, границы, пустые данные, повторные действия, ошибки. Для найденного дефекта полезна регрессия, обнаруживающая старую ошибку; не писать бессмысленные тесты ради числа.
3. **Взаимодействия.** База, очередь, API, файловое хранилище, авторизация, тайм-ауты, повторная доставка, частичный отказ. Mock не подтверждает реальную интеграцию.
4. **Работающее приложение.** Реальный путь пользователя, сохранение/повторное чтение, нужное устройство, загрузка и ошибка. Проверка скриншота не подтверждает серверное поведение; HTTP 200 не подтверждает удобство.
5. **Выпуск.** Реальный артефакт/версия, конфигурация, миграция и восстановление. Для нескольких процессов сверить совместимые версии всех затронутых компонентов.

Проверки в CI должны действительно запускаться, а не быть skipped/neutral из-за неверного условия. Указать обязательные jobs и их область. При наличии защиты ветки использовать её; невозможность настройки не маскировать инструкцией в Markdown. Изменения самих проверок включить в ревью.

Независимый анализ требований/исходников можно выполнить в обычном чате по [REVIEW_CHAT](REVIEW_CHAT.md). Запуск тестов и проверка работающего приложения при этом остаются отдельными доказательствами. Management фиксирует, кто и на какой версии выполнил каждый обязательный критерий. Для рисков, требующих независимого воспроизведения, нужен отдельный исполнитель со средой запуска; пакет с чужими логами этого не заменяет.

## Особенности продуктов

- **Веб:** поддерживаемые браузеры и размеры экрана; доступность ключевых действий с клавиатуры/читаемость; сессии, права, ошибки сети, сохранение. Нужен доступный владельцу HTTPS-preview или иной согласованный способ демонстрации, если localhost недоступен.
- **Telegram-бот:** отдельный тестовый бот/чат, отсутствие нежелательных рассылок, повторная доставка событий, идемпотентность действий, права и ограничения API. Mini App — серверная проверка подписанных данных входа и срока их действия, поведение внутри настоящего клиента, возвращение в приложение.
- **Мобильное приложение:** сборка целевой платформы, установка/обновление, разрешения, жизненный цикл, офлайн/сеть, устройство или эмулятор. Для iOS заранее обеспечить поддерживаемую macOS/Xcode-среду или соответствующий сервис сборки; сборка веб-части не равна проверке iOS-приложения.
- **Библиотека/CLI:** публичные контракты, установка в чистой среде, заявленные версии платформ, совместимость и опубликованный пакет/бинарник.
- **ИИ-функция:** контрольные примеры, критерии качества и типичные ошибки, цена/задержка, отказы провайдера. Не называть число вероятностью без обоснования. Разделять проверку транспорта/API и содержательную оценку модели; фиксировать версии промпта/модели/набора примеров. Реальные вызовы только в разрешённом бюджете.
- **Данные/платежи/доступы:** сценарий другого пользователя, повтор/конкурентность, частичный сбой, целостность, отсутствие утечки в логах; для миграции — существующие данные и восстановление. Для чувствительной публичной системы management отмечает необходимость профильной человеческой экспертизы, если ИИ-проверками нельзя обосновать готовность.

## Как классифицировать замечания

- **Блокирующее:** нарушен критерий задачи, есть существенная регрессия, риск несанкционированного доступа/потери данных или неподготовленный необходимый выпуск. Требуется исправление/решение до приёмки.
- **Неблокирующее:** улучшение, не влияющее на согласованную готовность. Не расширять им текущую задачу автоматически.
- **Гипотеза:** ещё не доказана. Описать способ проверки; не выдавать за подтверждённый дефект.

Недоступная обязательная проверка означает blocked для соответствующего критерия. Отчёт содержит область, доказательства, ограничения и заключение. Исключение из критерия принимает владелец явно; оно не исчезает из истории.
