## Проблема и результат

Сейчас `BatchFuse` предлагает выбрать тип/целевой уровень, вручную ввести количество, собрать пул и нажать «Рассчитать пакет». `FuseRequest` требует count, а планировщик при нехватке возвращает INSUFFICIENT_MODS. Владелец меняет сценарий и ограничивает массовый фьюз только полностью одинаковыми модами.

Результат: выбрать существующую пачку одинаковых модов → выбрать целевой уровень → автоматически увидеть максимум и расчёт → при необходимости уменьшить количество результатов → применить. Для20одинаковых🅾️1.0 по10 и цели3.0 сразу видны максимум2/цена1008/остаток2, без угадывания выходного количества и отдельной кнопки расчёта.

Новый контракт заменяет прежний массовый смешанный пул TASK-005/006. Игровые формулы/цены/сырьевые рецепты, обычный одиночный фьюз, крит, экипировка, сохранение/пополнение/reset, дизайн Sites, Telegram и гарантии данных сохраняются.

## Пользовательское поведение

### Выбор группы и цели

Исходник — одна существующая группа текущего work с одинаковыми kind/tier/value/crit. Разные исходные партии одинаковых модов, уже объединённые в рабочую группу, используются как общий запас. Пагинация не обрезает quantity группы до числа загруженных карточек; оставшиеся группы доступны штатной загрузкой.

Не предлагать для массового действия смешанный пул/сортировку входов/подбор нескольких разных статов. Выбрать группу можно в панели либо действием из её карточки; обычное решение компоновки developer принимает в текущем дизайне. Тип/характеристики исходника видны игроку и не вводятся повторно.

Цель строго выше исходной, до6.0. Для сырья — соответствующая обычная цепочка1–6, для остальных — s+1…6. Уровень6.0 не имеет следующей цели. Одну группу с неизвестным критом нельзя выдавать за известные одинаковые значения: предложить штатное «Уточнить крит» перед массовым применением, без подстановки0 и потери старых данных. Отсутствие крита у типов, где его нет, не блокирует массовый фьюз.

По умолчанию доступен ненадетый запас выбранной группы. Явная опция «Включить надетые» разрешает также её надетые экземпляры; ненадетые расходуются первыми. При снижении количества разрешённых для расхода входов расчёт максимума должен учитывать фактически разрешённое, не весь инвентарь. Не расходовать экипировку другой группы.

### Автоматический расчёт и количество результатов

После выбора/смены группы, цели или разрешения надетых автоматически показать актуальные:
- доступное количество исходных;
- максимум целевых модов и сколько исходных нужно на один;
- выбранное количество результатов, первоначально равное максимуму;
- характеристики результата, промежуточные переходы/цены, полный расход алмазов;
- расход исходных/снимаемую надетую часть и остаток.

Отдельная кнопка «Рассчитать пакет» для штатного сценария не нужна. Предварительный расчёт не мутирует source/work/equipment/revision/history/receipt. Результат приходит и без заранее выбранного count. Сервер получает выбранный исходник/цель/разрешение надетых и сам вычисляет максимум по актуальному stock; технический shape DTO/маршрута developer выбирает с учётом старых receipts.

Рядом с максимумом — одно целочисленное поле/ограниченный числовой выбор от1 доNmax, со значениемNmax по умолчанию. Пользователь уменьшает количество; цена/расход/остаток пересчитываются автоматически. Не генерировать список изNmax вариантов/DOM-элементов, когда максимум огромный. Точный ввод и отображение не ограничены JS Number.

При смене исходника/цели/разрешения надетых устанавливать новое значение максимума по умолчанию. При завершении ввода числа большеNmax привести выбор кNmax и явно показать допустимый максимум; пустой/нецелый/отрицательный/нулевой ввод даёт видимую ошибку до применения. Сервер также отвергает подменённое количество вне допустимого диапазона с понятной ошибкой, не молчит и не выполняет частичную операцию.

ПриNmax=0 показать0 и объяснение: «Для одного мода3.0 нужно9 модов1.0, доступно8». Применение недоступно, данные не меняются. Пустой выбор/недоступная цель/ошибка сервера также имеют видимое состояние.

Асинхронные ответы связывать с текущими source/target/count/stock revision: старый ответ после смены цели не заменяет новый. Кнопка применения недоступна при незавершённом/устаревшем расчёте. Изменение запаса между preview/commit даёт прежний конфликт и обновление данных с новым расчётом; не применять внезапно уменьшенный пакет без нового подтверждения. Потерянный ответ подтверждённой команды повторяется прежним payload/key, не переделывается в новый «максимум» на изменившемся запасе.

## Математика и строгое равенство

Для исходногоs и целевогоt>s: R=3^(t−s), Q=доступное количество одной группы, Nmax=Q/R с целочисленным делением. Сырьё имеет техническоеs=0. Применение n≤Nmax расходует ровноn×R исходных; остальные сохраняются исходными. Для максимального пакета не нужно дополнительно докрафтить оставшиеся единицы в низшие уровни. Наличие иных промежуточных/целевых модов не увеличивает максимум и не добавляет их в расход.

Все промежуточные результаты получаются исключительно из выбранной однородной группы. На каждом переходе соблюдать прежние ceil для урона/здоровья и ceil до0,001 для крита, цены по типу/получаемому уровню. Крит персонажа×3 в формуле фьюза не участвует. Результаты одной операции одинаковы по всем характеристикам; сырьё меняет kind по своему обычному рецепту.

Проверка однородности обязательна на сервере для **новых** массовых операций, не только фильтрация UI. Нельзя подмешать вторую группу с другим основным параметром/критом или уже готовые моды другого уровня той же семьи, обойдя форму. Предпочтителен запрос по одному work group ID, сервер читает фактические атрибуты/количества самостоятельно.

Исторические смешанные batch-операции остаются частью сохранённого эксперимента: их можно отменять и безопасно повторно получать уже записанный результат команды. Не уничтожать старые receipts/историю и не пытаться проверять прошлый ledger по новой однородной модели. Новый ключ с прежним смешанным payload не разрешает новый mixed batch. Одиночный craft трёх модов по прежним правилам не ограничивается этой массовой проверкой.

BigInt/decimal TEXT для количеств/стоимости/крита; integer Number допустим только для ограниченных уровней/индексов. Расчёт/план/история компактны по группам и максимум6переходам, без массива из физического количества модов/фьюзов. Сохранить обоснованные технические ограничения запросов, не вводить игровой предел инвентаря. Производный допустимый максимум не обрезать до128цифр только из-за старого size bound входного count.
